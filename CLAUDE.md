# KAVOPROVID — інструкції для Claude Code

Це головний файл правил проєкту. Claude Code читає його автоматично на початку кожної сесії.

---

## 1. ГОЛОВНИЙ ПОДІЛ: факти vs творчість

У цьому проєкті є дві принципово різні категорії роботи:

- **ФАКТИ про бренд** (тексти, кольори, лого, шрифти, обладнання) — беруться **ВИКЛЮЧНО** з файлів проєкту. Нічого не додумувати, не доповнювати, не «покращувати» правдоподібними деталями.
- **ВІЗУАЛЬНІ Й ДИЗАЙН-РІШЕННЯ** (layout, анімація, структура сторінок, окремі fun-фішки) — тут, навпаки, очікується **творча ініціатива**. Пропонуй сильні, продумані рішення, а не мінімально безпечні.

Ці два режими не можна плутати: не вигадуй фактів, але й не бійся пропонувати дизайн.

---

## 2. ДЖЕРЕЛА ПРАВДИ (факти — тільки звідси)

Усі факти про бренд KAVOPROVID беруться з файлів нижче. Якщо потрібного факту немає в жодному з цих файлів — **став запитання власнику, а не вигадуй відповідь.**

> ⚠️ Уточни й підправ шляхи нижче під свою реальну структуру папок проєкту — я не бачу твоєї файлової системи, тому шляхи orientовні.

| Що це | Де лежить (приклад — підстав свій шлях) | Що звідти брати |
|---|---|---|
| Повний аудит брендбуку | `docs/KAVOPROVID_Brandbook_Audit_FULL.md` | Позиціонування, місія, цінності, tone of voice, формула бренду, значення двох ліній, патерну, правила брендування |
| Оригінальний брендбук (PDF/зображення) | `docs/brandbook/` | Візуальні макети-приклади — звіряти дизайн-рішення з реальними сторінками |
| Файли логотипу | `docs/logo/` (PNG/SVG/PDF, усі варіанти: базовий, скорочений, трафаретний) | Тільки ці файли. Не перемальовувати логотип текстом чи CSS |
| Шрифт Gilroy | `docs/fonts/` (усі отримані `.ttf`/`.otf`) | Підключати лише реально наявні нарізки. Якщо якоїсь ваги немає — не імітувати її штучним потовщенням/утонченням, писати про це прямо |
| Фото кавомашин | `docs/machines/photos/` | Реальний вигляд обладнання — не вигадувати інші моделі чи ракурси |
| Характеристики кавомашин | `docs/machines/specs.md` (або як у тебе названо) | Точні технічні дані. Ціни, гарантії, умови оренди — тільки якщо є в файлі |

**Правило перевірки перед кожним фактом:** «Чи є це дослівно чи по суті в одному з файлів вище?» Якщо ні — це TBD, не факт.

## 3. ТВОРЧА СВОБОДА (тут можна й треба пропонувати)

На відміну від фактів, тут очікується самостійна дизайнерська пропозиція, а не мовчазне копіювання брендбуку 1:1. Орієнтир — бренд-концепція «інфраструктура безперервної кави / кавовий потік», а конкретне втілення — на розсуд Claude Code.

Можна й потрібно пропонувати:
- **Layout і структуру сторінок** — які секції, у якому порядку, що йде на головну, що на внутрішні сторінки.
- **Анімацію та motion** — як передати ідею потоку/проводу/безперервності в русі (скрол-ефекти, hover-стани, перехід між секціями).
- **Окремі фірмові «фішки»** — нестандартні, але доречні деталі, які підсилюють впізнаваність (наприклад: фірмові дві лінії як наскрізний елемент, що «прошиває» сторінку; курсор у вигляді краплі; лічильник чи індикатор у дусі «потоку» тощо — це приклади напряму мислення, не готове рішення).
- **Ілюстративні елементи**, які не суперечать забороні на кавове зерно/чашку в лого, але можуть з'явитися деінде, якщо це підсилює ідею інфраструктури.

**Єдине обмеження творчості:** нові пропозиції не повинні вигадувати нові факти про бренд (нові кольори, нову obіцянку, нові послуги) — вони можуть тільки по-новому подавати вже підтверджені факти.

## 4. РОБОЧИЙ ПРОЦЕС

1. Перед будь-якою зміною — прочитати актуальний стан коду/сторінки, яку редагуєш.
2. Не ламати те, що вже працює, без причини.
3. Перед великими дизайн-рішеннями — коротко описати пропозицію (2–3 речення: що і навіщо) перед тим, як писати багато коду.
4. Якщо в файлах джерел є суперечність (наприклад, різні контакти на різних макетах) — показати це як окреме питання, не обирати самостійно.
5. Якщо чогось не вистачає для завдання (даних, зображень, специфікацій) — прямо сказати, що саме бракує, замість того, щоб імпровізувати.
